# Agent Note: Claude subscription-session provider

Status: implemented

## Problem

The Claude subscription (Pro / Max) a machine's Claude Code CLI is signed in to was reachable from shres-code only by spawning the CLI binary: the `claude-code` delegated route in `llm-cli-bridge` and the `subagent-claude-code` backend. Unlike the Grok and Codex subscriptions, no HTTP adapter billed the subscription the way the CLI does. The user asked for that story's third step: a native route over api.anthropic.com carrying the CLI's own login credential. The credential sources here are unofficial and the machine's own CLI login was expired during implementation, so every wire fact below comes from pi-ai's installed sources, the installed CLI binary, or the CLI's documented login, and the live probes are listed under Testing.

## Decision

Three pieces: `packages/llm/claude-credential` (the single-flight credential engine, `ctx.claudeCredential`), `packages/llm/llm-claude-session` (the `claude-session` route over the shared pi-ai adapter), and one shared-package change in `llm-pi-ai` that lets a hand-declared `anthropic-messages` route state what pi-ai's own catalog states for these models.

**What pi-ai already owns, so nothing here re-implements it** (read from `@earendil-works/pi-ai@0.84.1`, `dist/api/anthropic-messages.js`). `isOAuthToken(apiKey)` is `apiKey.includes("sk-ant-oat")` (line 640); on detection the Anthropic SDK client is built with `authToken` (Bearer) instead of `x-api-key`, `baseURL = model.baseUrl`, and default headers merged from `{accept, anthropic-dangerous-direct-browser-access, anthropic-beta: "claude-code-20250219,oauth-2025-04-20[,fine-grained-tool-streaming-2025-05-14][,interleaved-thinking-2025-05-14]", user-agent: "claude-cli/2.1.75" (pinned const, line 39), x-app: "cli"}`; `buildParams` then prepends `system[0] = {type: 'text', text: "You are Claude Code, Anthropic's official CLI for Claude."}` ahead of the harness system prompt. That header merge is `mergeHeaders(oauthDefaults, model.headers, optionsHeaders)` — plain `Object.assign`, later sources win.

**No `headers` on the route profile, and one header the route cannot keep.** The merge above decides the first: a configured header of the same name would destroy the OAuth beta set rather than add to it, so the section exposes no `headers` field and `tests/route.spec.ts` pins that the resolved profile carries no `headers` property. The second is Harness app attribution: `shres-code-llm-pi-ai` passes `userAgent()` as pi-ai options headers, which win the same merge, so this route's outgoing `User-Agent` is the harness identity rather than pi-ai's pinned `claude-cli/2.1.75` — attribution is mandatory on every provider request by [its own Agent Note](2026-06-21-mandatory-app-attribution-headers.md), and no route setting can suppress it. The remaining CLI identity — the betas, `x-app`, and the identity system block — is intact, and `tests/loader-composition.spec.ts` pins the value that actually leaves. The same ownership settles the `?beta=true` question: the Anthropic SDK builds `baseURL + "/v1/messages"` with no query, and neither a base URL nor a header can smuggle one, so if the subscription endpoint turns out to require it the fix is a pi-ai upgrade, not a local fork (Testing).

**Credential sources.** The CLI stores the login as one JSON document: the macOS login keychain's `Claude Code-credentials` item (`security find-generic-password -s "Claude Code-credentials" -w`, deliberately without an `-a` filter) on macOS, `~/.claude/.credentials.json` elsewhere — the CLI's own platform split, resolved explicitly in `resolveCredentialSpec` as `useKeychain ?? (process.platform === 'darwin')`. The credential spec also carries `securityPath` (`/usr/bin/security`) and `keychainAccount` (`os.userInfo().username`) because a rotation must write under an account the CLI will find, and `authPath`. The service memoizes one manager per all-five-fields key.

**Document shape and selection.** The document is `{ claudeAiOauth: { accessToken, refreshToken, expiresAt, refreshTokenExpiresAt, scopes, subscriptionType }, mcpOAuth, … }`. `selectSessionEntry` requires a JSON object carrying a `claudeAiOauth` object with a non-empty `refreshToken`, and refuses an absent `accessToken` beside a non-zero `expiresAt`; `MISSING_CREDENTIAL` is reserved for a store that is absent, unparseable, or holds no usable session, and the file source additionally asserts owner-only mode. No diagnostic quotes a credential value; every recovery step names `claude` and its `/login`.

**`expiresAt: 0` and `refreshTokenExpiresAt`.** A stored `expiresAt` of zero states that the store holds no access token — a refresh token without a token yet — not that no credential exists, so it is at-or-past expiry by construction and runs the refresh instead of failing. A `refreshTokenExpiresAt` already past refuses the grant, but only after the sibling-adoption re-read: the CLI may have signed in again since, and a single-use refresh token must not be spent on a request that cannot succeed. The refusal is `AUTH_REFRESH_FAILED` naming the sign-in step. A non-positive `refreshTokenExpiresAt` counts as not stated.

**Refresh and rotation.** `POST https://console.anthropic.com/v1/oauth/token` with `{grant_type: 'refresh_token', refresh_token, client_id: '9d1c250a-e61b-44d9-88ed-5944d1962f5e'}` (the CLI's own login client). A grant must carry a non-empty `access_token` **and** a rotated `refresh_token` — both rotate, and storing a grant that withheld one would strand the store on a token the issuer has consumed — plus an expiry read from `expires_at` as epoch milliseconds, the store's own convention, with `expires_in` seconds as the fallback. The rotation merges field-wise over the latest re-read document so `mcpOAuth`, unknown root siblings, and `claudeAiOauth` fields the grant does not restate survive, then writes: a staging file beside the document at mode 0600 followed by `rename`, or `security add-generic-password -U -s "Claude Code-credentials" -a <account> -w <json>`. On both the grant-failure and grant-success paths a re-read sibling whose refresh token differs and is still valid wins over our own rotation, so a concurrent CLI refresh is adopted rather than clobbered.

**Reasoning efforts.** `{ off: null, low: 'low', medium: 'medium', high: 'high', xhigh: 'xhigh', max: 'max' }`. `off` is genuinely servable: pi-ai sends `thinking: {type: 'disabled'}` whenever the model's `thinkingLevelMap.off` is not pinned `null`, and pi-ai's own catalog pins no `off` for these models, so leaving the level's value empty keeps it offered with the correct dispatch. `minimal` stays undeclared — the wire has no honest spelling and pi-ai's fallback would alias it to `low` — mirroring the codex route.

**Catalog.** `claude-opus-5` and `claude-sonnet-5` with 1,000,000 context, 128,000 output, `text`+`image`, and adaptive-thinking compat, taken from pi-ai's shipped `providers/data/anthropic.json` (`claude-opus-5`: `compat: {forceAdaptiveThinking: true, supportsTemperature: false, supportsStrictTools: true}`; `claude-sonnet-5`: the same without the temperature pin); both ids are also present in the installed Claude Code CLI 2.1.232 binary. No Opus 5.5 id ships: neither source names one, and shipping an unverified id would betray the catalog evidence rule. A deployment adds it through the settings `models` entry (the catalog is trivially overridable), and the post-login probe in Testing confirms or discovers the id.

**The one shared change: the `llm-pi-ai` compat extension.** The route key `claude-session` is not an installed pi-ai provider, so `resolveRouteModels` finds no catalog entry for any of its models and inherits no `compat`. Without the extension, such a model would take the budget-thinking path and would send `temperature` — contradicting pi-ai's own metadata for exactly these models. `PiAiCompatProfile` therefore gains `forceAdaptiveThinking` and `supportsTemperature`, typed `anthropic-messages`-only exactly as `thinkingFormat` and `supportsReasoningEffort` are typed `openai-completions`-only: a model-level switch of the other family fails resolution naming the protocol, a route-level default skips models of other protocols, a route-level switch no model on the route can take is refused, and the existing `base?.api === api` inheritance rule is unchanged. pi-ai's own `AnthropicMessagesCompat` documents this use, and `api/anthropic-messages.js` reads both fields (lines 118 and 751-786) to select `thinking: {type: 'adaptive'}` with `output_config.effort` and to withhold `temperature`.

**Ship posture.** Mounted in the base bundle beside the cursor, codex, and grok session rows and in `shres models`, enabled and dormant: listing and selection work without a login, and the first request fails loud with `MISSING_CREDENTIAL` naming the sign-in. The directory entry carries no `chatGated` — unlike the cursor route, this one serves chat over a replicated wire.

## Alternatives considered

**Fork pi-ai, or carry the OAuth header set and the identity block in the route profile.** Rejected: pi-ai already owns the beta set, the identity block, and the pinned CLI user-agent, and a configured header of a name pi-ai sets would win the later-wins merge and destroy the value pi-ai put there. The `onPayload` hook would be the only local place to add a query the SDK never builds, which is a fork in disguise.

**Hand-roll the adaptive/disabled thinking dispatch through `onPayload`.** Rejected: pi-ai's `streamSimple` already chooses adaptive versus budget from `compat.forceAdaptiveThinking` and disables thinking through the level map, so expressing the requirement as compat configuration keeps the request on the stock dependency and the behavior unit-testable at the catalog layer.

**Extract one generic "CLI OAuth session" engine shared with the codex, grok, and cursor engines.** Rejected for the reason the [codex note](2026-09-06-codex-session-provider.md) gives: the documents share no shape, no grant encoding, and no account-header concept. The genuine symmetry is the single-flight/adopt/persist pattern, mirrored deliberately rather than parameterized, with jscpd markers on the lifecycle boilerplate alone so engine-body drift stays visible.

**Treat `expiresAt: 0` or a past `refreshTokenExpiresAt` as `MISSING_CREDENTIAL`.** Rejected: both states name a credential that exists and a repair the refresh grant can still attempt, so reporting a missing credential would tell a user to sign in again when a rotation is what the request needs.

**Serve the credential through the credentials seam.** Rejected as for grok and codex: that seam resolves a static reference and has no refresh semantics, so a subscription login would go stale.

## Testing

`packages/llm/claude-credential/tests/session.spec.ts` pins selection, the leeway decision, the grant and the `expires_at`/`expires_in` parse, sibling adoption on both paths, the `refreshTokenExpiresAt` refusal (with no fetch call), rotation persistence that preserves `mcpOAuth` and unknown siblings, and both write paths; `tests/service.spec.ts` pins the memoization and disposability. `packages/llm/llm-claude-session/tests/loader-composition.spec.ts` boots the real composition through the Loader and drives one request against a loopback Anthropic SSE stand-in, asserting `POST /v1/messages`, the `sk-ant-oat` bearer, `anthropic-beta` containing `oauth-2025-04-20`, `x-app: cli`, the identity block as `system[0].text`, adaptive thinking with `output_config.effort`, thinking disabled for the `off` effort, the `User-Agent` the wire actually carries, and disposal. `apps/cli/tests/models-cli.spec.ts` pins the route in the provider listing and a default selection without a stored login. No keyless ACP or headless transcript is expressible for a credential-gated route, which is why the codex and grok routes' precedent — real-composition loader tests plus models-cli pins — is what this route ships; `packages/llm/llm-pi-ai/tests/catalog.spec.ts` and `config.spec.ts` cover the compat extension, including the protocol mismatches it refuses.

The engine's default `security`-tool paths execute a POSIX script stand-in, so `vitest.config.ts` exempts `packages/llm/claude-credential/src` from the Windows coverage lane the way the bash-local suites are exempted; the injected-hook tests cover that engine on every platform.

Open live-verify items, each with a named owner: `?beta=true` (pi-ai upstream if required), effort `off` accepted as `thinking: {type: 'disabled'}` on an adaptive model (route catalog if not), the `expires_at` unit confirmed by one forced rotation (grant parser), the served model ids from `GET https://api.anthropic.com/v1/models` with the OAuth bearer and the `oauth-2025-04-20` beta (route catalog), and whether the subscription endpoint accepts the harness `User-Agent` in place of pi-ai's CLI one (an attribution-versus-CLI-identity decision in `shres-code-llm-pi-ai`/pi-ai if it does not; the beta set and `x-app` already leave as pi-ai sends them). All five wait on a fresh `claude` + `/login` on the machine.

## Consequences

The credential sources and the request identity are the Claude Code CLI's implementation details: the keychain service name, the `claudeAiOauth` field names, the `claude-code-20250219` / `oauth-2025-04-20` betas, and the identity system block can move under a CLI update, and the request-time error names the sign-in step. The beta set belongs to pi-ai, so a server-side floor bump or a new required beta is a pi-ai upgrade (the grok route's 426 precedent), while the user-agent half of that identity is replaced by mandatory Harness attribution on the wire and is the live-verify item whose owner Testing names. Because the refresh token is single-use, concurrent refreshes are resolved by adoption after the fact rather than prevented; the keychain account must match the CLI's or the item lives on untouched. Adaptive thinking is what these models require, so the request no longer carries a token budget, and `temperature` is withheld on Opus 5.

This worktree's `pnpm run gen-cordis-catalog` (and therefore `verify-cordis-catalog`, `verify-doc-graphs`, and `doc-sync`) already fails before this change: the cursor packages' `ctx.cursorCredential.managerFor` signature references `CursorSessionManager` / `CursorSessionOptions`, which `scripts/gen-cordis-catalog.ts` neither maps to a doc page nor exempts, and `cursorCredential` has no `SERVICE_PAGE` entry or subsystems page either. That gap is the cursor change's own to close, so the generated catalogs here were left to the generator and the two claude entries added to its maps are what the next successful run consumes.
