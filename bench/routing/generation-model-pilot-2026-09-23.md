# Generation model routing pilot

This preregistration defines a functional data pilot for routing supervision. The two direct generation baselines use the existing `off` arm, the same task catalog, temperature, concurrency, verifier, and runner, with the provider/model tier as the intended varying factor. The pilot is descriptive and cannot promote a model, replace JEV or Laya, or use a model judgment as a task label.

The readiness gate runs one `single-function-fix` trial for each model, for two canary trials total. Each canary command runs once with `--repeats 1`, `--concurrency 1`, no `--resume`, and `--max-total-tokens 16000`. The launch script stops immediately on a nonzero runner exit, a provider or harness error, a missing session route, or an observed `request/header` route that does not match the configured provider/model. The main pilot starts only after both canaries pass.

The main pilot has six tasks and three repeats per model, for 18 trials per model and 36 trials total. The selected task IDs are `single-function-fix`, `cross-module-refactor`, `chain-debug-resume`, `injection-ignore`, `constraint-survival-build`, and `noise-needle`. They cover short, long, chain, adversarial, and pressure strata. The runner uses `--temperature 0`, `--concurrency 1`, and `--max-total-tokens 120000`.

The runner's token option is a live observed root-plus-descendant usage cap per spawn. It is applied independently to each phase of the two-phase chain task, and it can terminate a task with `BUDGET_EXCEEDED`; it is not a hard pre-request or whole-chain total. The current profile exposes task wall timeouts through each task definition; the selected task timeouts are 300 seconds for short tasks, 600 seconds for the long and chain phases, and 900 seconds for pressure tasks. The serial main pilot has a configured wall-time upper bound of about 7 hours before process overhead, based on 42 spawns across both models and the pinned task timeouts. There is no supported shared model-output `maxTokens` overlay in the `agent-default-model` tier patch, so the pilot records the runner cap and task timeout semantics without claiming a per-request output cap.

The configured model pairs are `zai/glm-5.2` through `bench/tiers/zai.patch.yml` with `ZAI_API_KEY`, and `ollama-cloud/deepseek-v4-flash:cloud` through `bench/tiers/ollama-deepseek.patch.yml` with `OLLAMA_API_KEY`. The runner resolves credentials from exported environment variables or the existing credential store and never writes values to a run record. Missing or invalid credentials fail the canary before the main pilot. The Ollama `:cloud` tag is a floating provider alias; the registration records it as a configured identifier and records request-header routes, assistant response provenance routes, durable assistant IDs, and any provider response IDs separately. A request header matching the alias does not prove an immutable backend revision, so this pilot cannot claim weight pinning for that arm.

The quality label is the task verifier's `resolved` boolean on a `status: success` trial. `VERIFY_FAILED`, `AGENT_TIMEOUT`, and `BUDGET_EXCEEDED` remain observed unresolved quality outcomes. `PROVIDER_ERROR` and `HARNESS_ERROR` rows remain in `trials.jsonl` and the analysis but are excluded from correctness labels. Pairing uses only equal `taskId` and `trialIndex` rows that both have eligible labels. Input and output token totals and duration are descriptive measurements only; no price table is assumed.

JEV, Laya, shield judgments, model routing decisions, and security detector predictions are never gold for these labels. The existing fixture verifier and its task definition are the source of task outcomes. The runner gives every trial a fresh scratch directory and session root, and both providers use the same direct `off` arm, which limits cross-arm state leakage. The selected task fixtures and tier patch contents are SHA-256 fingerprinted before launch.

Run the plan without network activity with `node bench/routing/model-pilot.mjs plan`. The canary-only command `node bench/routing/model-pilot.mjs canary --execute` writes the registration once and runs both canaries, collecting independent provider evidence before returning a failure. After both canaries pass, the explicit main launch `node bench/routing/model-pilot.mjs launch --execute` reuses and verifies that registration and runs the two main model commands sequentially. Analysis reads only completed artifacts with `node bench/routing/model-pilot.mjs analyze`.

At launch, the script records `HEAD`, a dirty-tree SHA-256, selected task and tier patch hashes, and an isolated local source snapshot commit under a content-addressed ref below `refs/shres/model-pilot/generation-model-pilot-2026-09-23/`. The snapshot uses a temporary Git index, excludes generated `bench/runs/**` and the registration itself, and leaves the current branch and user index unchanged. This local ref is the reconstruction point for the exact dirty source used by the run; it is not pushed.

The main launch checks the dirty-tree fingerprint before starting and after each model command, and analysis refuses to report quality when the current tree differs. The source ref preserves provenance but does not create a separate worktree, so the operator must keep the worktree frozen for the duration of the pilot.

This pilot is a wiring and data check, not routing promotion evidence. A larger separately registered random holdout is required before fitting or evaluating a routing policy, with provider availability, observed model identity, verifier quality, cost, and security labels kept as separate fields.

## Post-registration analysis amendment (2026-09-23)

The frozen registration and its recorded task, model, and patch fingerprints are unchanged. The analyzer now validates every trial row against the on-disk trial schema before reading it, requires session evidence for successful trials, and fails closed when a referenced session log is missing. Infrastructure failures that occur before a session exists remain retained as non-label rows; a successful resolved row with no request or response route is an evidence error, while an unresolved attempt must have request evidence and may have no assistant response when the run timed out or exhausted its budget.

The quality label remains the runner's verifier `resolved` field. A separate recorded execution budget stop is reported as budget evidence and does not rewrite a verifier pass into a failure. Provider-reported nested response model identifiers remain descriptive provenance: a missing identifier is unknown configured-service evidence, while an identifier that differs from a registered fixed model excludes that trial from quality labels and matched pairs. The raw trial row remains in the analysis, with a per-trial exclusion reason. A floating provider tag may pass readiness without a reported backend model, but neither that case nor any other unknown identity supports a model or weight pin claim; fixed-model canary drift fails readiness.
