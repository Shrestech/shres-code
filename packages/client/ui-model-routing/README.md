# @shres-code/shres-code-client-ui-model-routing

Model-routing status chip and per-session Routing view, a pure browser surface plugin. The browser half occupies the conversation-declared `conversation.input.modelRouting` single seat in the composer tool row, immediately left of the model-select seat; the node half is an empty apply (the roster row). Routing itself — the `/route` command, the two log-only routing events, the sticky fold, and the `modelRouting` projection — is owned by [`@shres-code/shres-code-model-router`](../../llm/model-router/README.md), composed independently on the host roster.

The chip reads the host-computed `modelRouting` projection through the framework `useProjection` seat and holds no routing state of its own. It states the routing mode alone: while the projection's `active` is false the button is the `Auto` affordance that executes `/route on`, and while it is true the button reads `auto` and executes `/route off`. The chip names no routed model, no confidence, no streak position, and no model hint: those render in the trajectory and the full session log, where inspection is deliberate. An ambient routed route on the chat surface invites the manual pick of it, which dead-ends routing — the session's own selection becomes a pool candidate, so every later decision resolves `base-unlisted` (routing does not start from a pool model) or, when that model is also listed in `routeFrom`, `candidate-equals-base`, and nothing can downgrade. Each of the two reasons has its own idle warning.

A session in that state renders the routing-idle warning beside the chip, plus a one-click `Restore strong model` control. The restore submits the projection's retained `lastStrong` route — the route the last downgraded streak was entered on, kept after that streak broke — through the session's model-selection directory (`ctx.modelDirectories`, the same `ModelDirectory.select` the composer picker and the `/model` popup submit through), so the session's own selection changes and no second selection mechanism exists. That service is optional: a deployment composing no model-selection surface keeps the chip, and the restore reports the absence in its own inline failure line. The restore's copy states what the selection change costs: one prefix re-prefill on the next request.

Admission failures (`matched: false`, business errors, transport faults) surface as an inline error line while the chip stays until the projection confirms the change, and a gesture in flight disables both controls and reports `aria-busy`. Each gesture keeps its own English failure label, because a refused selection is not a refused mode switch.

Turning routing on is the gesture that starts sending conversation state to the judge, so while the selected judge's egress is `remote`, or before the engine facts are known, the chip opens a confirm first: it names the destination host (the engine label when the provider names none) and the per-consult character cap, and routing turns on only from its Turn on button. A local judge, or none, turns routing on directly, and turning routing off never asks.

Absence is the one mode the seat draws nothing for: a host composing no router registers no `modelRouting` projection, so the seat renders nothing at all and an unoccupied seat costs no layout. Addressed subagent sessions render nothing either, through the same `sessions.subagentAddress` guard the model seat uses, because the Agent-bound command channel would activate persisted child history outside the direct-parent continuation path.

A flip requests the mode through the command line a user could equally type, and the host commits it as a logged mode event — between turns at once, during an open turn at the next accepted pre-step. The chip's own in-flight state covers that wait; the projection's `pending` field is not mirrored, because the requested mode is already visible as the gesture's own feedback and a second client-side read of it would be a copy of host state.

## Routing view

The browser half also registers a `conversation.view` entry, id `routing`, order 20, so the session's Activity popover lists `Routing →` after Chat and Trajectory, and selecting it replaces the session body. The entry is listed while the host composes `@shres-code/shres-code-model-router`, read from the `model-router` settings namespace the router installs only while it is mounted: the plugin binds that namespace's settings scope and keeps the entry registered while the scope is `loading` or `ready`, disposes it when the scope reports `unavailable`, and registers it again when the namespace returns. Listing it while `loading` keeps a persisted Routing selection on its view during page load; when the entry is gone, the conversation shell shows Chat without writing the stored selection, so the view returns with the router. The view holds a skeleton while the scope is `loading` and while the session's projections have not arrived with its tail page; after that, a session without the `modelRouting` projection, or an addressed subagent session, reads "Routing isn't available for this session". The view reads only its own session: the host-computed `modelRoutingStats` projection (counts, histograms, the step timeline, and the 200 most recent decisions, folded by `@shres-code/shres-code-model-router`) and the `modelRouting` projection for the mode. Two unary reads on the `modelRouting` Remote namespace complete it: `gate()` returns the configured thresholds, deadline, and difficulty scores, which decisions do not record, and `decision(sessionId, seq)` returns one logged decision for the drill-down. An addressed subagent session renders a notice instead, through the same `sessions.subagentAddress` guard the chip uses.

The view states the mode read-only ("Auto routing: Off · switch with Auto in the chat input"); the Auto chip is the only control. The same line names the judge the router's asks go to, shared by all sessions: its label, a status dot and lifecycle state, its egress (Remote · egress, Local, or No egress), and Uncalibrated unless the engine is calibrated. The judge is resolved as the dispatcher resolves it: a `model-router` entry in the `judgment` overrides applies only while that consumer is declared, otherwise the deployment engine answers; judgment switched off, an engine id no engine registers, or a host without the dispatcher reads as no judge. While routing is on and the judge is remote, a warning names the destination host and the per-consult character cap (`gate().stateMaxChars`). Below it are the state notices (no engine, a selected judge that is not ready, a manual model outside Route from, recorded engine failures), the verdict sentence, eight KPI tiles, the model timeline (G1), confidence against the threshold (G2), decision reasons (G3), tokens by model (G4), cold prefills by cause (G5), judge latency (G6), streak exits, and the recent decisions, fifty per page. A session with routing Off and no decisions shows an empty-state card instead. Each graph is hand-built SVG with a `<title>` and a text alternative generated from its data, a Table toggle that renders the same data as an HTML table, and that table kept visually hidden otherwise so screen readers read it by default; marks are focusable, and focus or hover writes the mark's text to the card's live detail line. Colours are the `--dsw-alias-chart-*` aliases from `ui-theme`; the strong model is always `chart-strong`, pool candidates take `chart-series-1` to `chart-series-5` in pool order, and each model also has a marker glyph, so colour is never the only channel. Numbers are tokens, shares, and milliseconds; no price or dollar figure appears.

Selecting a timeline dot or a decision's turn opens the drill-down: the engine facts (with the registry id, eligibility time, judge tokens, and a warm-up when the decision recorded them), the route question, the option probabilities, confidence and margin against the thresholds, difficulty against the entry and exit scores, the ordered gate path with its first failing check (pool and state, listed base, cooldown, engine, eligibility, judgment call, difficulty, keep-current, confidence, margin, streak rules, in the router's order; an engine refusal after the eligibility assessment, from the re-check before asking or the answering engine, stops at the judgment call), candidate eligibility, the state sent to the judge (its text only on request), and the streak facts. A timeline step, a decision's `Trajectory →`, and the drill-down's `Show in Trajectory →` hand off through the conversation shell's `reveal` request with an event target, which Trajectory resolves to the record containing that seq; Trajectory's `Explain` on a ROUTING row hands back with the decision seq, which opens its drill-down. The links render only when `canReveal('trajectory')` reports the view.

The `/client` exports are the plugin body (`apply`/`inject`), the seat's injected face type, and the Routing view's injected face type.

## Model Experience

Indirectly, through the `/route on` and `/route off` command lines the chip dispatches and the model selection the restore submits: `@shres-code/shres-code-model-router` owns the logged mode, the sticky fold, and the route the consult selects for the next turn, while this package only renders the projection, sends what a user could equally type, and submits a selection through the selection surface's own path.

#### KV Cache effect

Ending or starting a downgraded streak is what puts the next turn on another route, and that transition is the re-prefill the streak bounds; the chip itself adds no prompt content. The restore is the one deliberate selection change this package can cause, and it pays the same cost once: the next request re-prefills its prefix, which is why the control states that cost and is offered only while routing is idle, where no held streak is amortizing anything.

## Known Limitations and Deferred Work

- **A session that never entered a downgraded streak has no route to restore** — the idle warning renders alone, because the projection carries no entry base to point the selection back at.
- **The mode and the restore are the only routing controls here** — the candidate allowlist, the gate thresholds, and the judgment engine are host composition plus the `model-router` settings namespace; the chip neither reads nor writes them.
- **The chip belongs to the default composer** — a pending whole-composer interaction such as an approval or question takeover replaces the InputBar and its chip.
- **Judge facts are read, not written** — the plugin reads `judgmentEngines.snapshot()` once on load and again on each `judgment/engines-updated` announcement (engine registration, status, consumers, and `judgment` settings commits), into one source both the view and the chip select from; an unavailable Remote reads as no dispatcher. The status line names Settings › Model routing as text: no client service opens a Settings page from a plugin.
- **Sent off-machine counts remote judges only** — a decision names its engine as the provider reported it, matched against registry ids and then labels; a name the current registry does not know is not counted, and before the registry answers the tile reports the egress as unknown.
- **Thresholds at the time, else now** — the drill-down compares a decision with the confidence and margin floors it recorded as applied, labelled "threshold at the time" with their origin (the engine's operating point or the global defaults) and the preregistration that calibrated them, or "uncalibrated". A decision that recorded none (a failed or late call, a refused engine, a skip) is compared with the floors in force now for the engine it names, from `gate()`: that engine's operating point, else the global floors, labelled "threshold now" with the calibration they carry. Entry and exit difficulty scores come from the decision when its consult asked the difficulty question, else from `gate()` now, which the drill-down states. The charts, the verdict, and the tiles use the floors the current judge is gated by now (its operating point, else the global floors), and G2 notes consults that recorded other floors.
- **Every served model has its own row** — G4 and the timeline legend list each model that served calls; models past the fifth candidate share the neutral `other` colour and keep their marker glyphs, and no synthetic "Other" row aggregates them, so a session with many models draws a long G4.
- **Graphs scale rather than re-lay out** — each graph is an SVG with a fixed `viewBox` that scales to its card, and the KPI and graph grids stack into one column when the view is at most 560 px wide (a container query); marks and labels do not re-flow at intermediate widths.
- **Idle expiry uses an assumed 5-minute cache lifetime** — G5 states it, because the log does not record the prompt-cache retention in force ([model-router limitations](../../llm/model-router/README.md#known-limitations-and-deferred-work)).
- **Latency covers what the log records** — an ask's latency adds its eligibility assessment when the decision recorded it; G6 notes when the log records the judgment call only.
