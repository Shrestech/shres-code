# @shres-code/shres-code-client-ui-settings-model-routing

Browser Settings page for model routing configuration that applies to every session. It registers a `settings.section` row (`id: model-routing`, order 10.5, directly after Models) while the Host serves the `judgmentEngines` Remote, and removes it when a read reports that no judgment dispatcher is composed. The page header carries the pill "Applies to all sessions"; per-session routing stays with each session's Auto chip.

The page has three cards:

- **Judgment engine.** A selector over every engine the Host's registry lists (`judgmentEngines.snapshot()`), each option naming its egress; an engine whose descriptor requires another host is listed but disabled. The selected engine shows its live state (with the provider's detail while not ready), its egress badge ("Remote · egress" or "Local"), and its model ids. Changing the selection writes `judgment.engine` through the settings seam with the section revision; a rejected write shows its message beside the selector, prefixed by the field path when the owner named one (`SettingsFieldError`). Below it, **Consumers** lists every declared judgment consumer with the engine the dispatcher asks for it: the consumer's `judgment.overrides` entry while the consumer is declared, else the selected engine (marked "Override" or "Selected engine"), with that engine's egress; an override naming an engine that is not composed, and an override for an undeclared consumer (which the dispatcher ignores), are listed as such. The `model-router` row adds how the router gates that engine, read from `model-router.operatingPoints` and the engine's calibration: "Calibrated (<calibratedBy>)", "Uncalibrated: operating point thresholds", "Uncalibrated: global thresholds", or, for a verbalized engine whose point does not set `acceptVerbalized`, "Not used for routing: verbalized, no accepting operating point". The egress notice then covers those consumers: while any consumer's engine is remote (off this machine, including a host on the local network), a warning names each such consumer with its engine and destination and what it sends (for `model-router`, each consult's bound from `state.maxChars`, or `state.maxFitCandidates` alternatives of at most that size for a fitting engine; for any other consumer, every ask, whatever the routing mode), and says it also appears when a session turns routing on when the router is among them. Otherwise a note says why nothing leaves this machine: the classifier is off, no consumer is composed, or every consumer asks a local engine. When the registry lists `laya`, the card adds the Laya row: gateway state, pinned artifact, context size, and Install, or Restart and Reinstall… (after a confirmation), through the `laya` Remote, which runs the same operations as `/laya`.
- **Default for new sessions.** Off / On writes `model-router.initialMode`. This is the only place the default is shown or edited; a session's own choice through the Auto chip is unaffected.
- **Classifier.** The `judgment.enabled` switch, moved here from the Models page; off makes every judgment consumer treat the engine as absent.
- **Candidate pool and Route from.** One editor holds both lists and writes them in a single settings write, so a pool edit and a Route from edit never race. "Add model…" picks from the same `llm.models` catalog the Models editor uses, or names a route by hand; each row carries an id auto-slugged from the model id and editable, a reasoning-effort select fed by the model's declared efforts, and a description with a counter that warns from 120 characters and stops input at the 160-character limit. The hint under the description names the judge's token budget while the routed engine is the local Laya gateway. Notes beside a stored row come from `modelRouting.poolStatus()` and name capability and token facts only: where a model is eligible from, where it never is and why, cross-membership with a Route from model, an unregistered route, and a provider that reports no cache counts. Route from lists one entry per enabled strong model; an entry stays in the unsaved draft until its objective (quota, dollars, latency) is chosen, and every-turn entry is a separate opt-in allowance on a quota route. A rejected write shows the Host's message beside the row its field path names, or beside the list, and nothing is published until the write commits.
- **Thresholds.** Read-only values from `modelRouting.gate()`: the confidence and margin floors, the difficulty band, the judge deadline, the hold, the state cap, and each engine's operating point with how the router gates it — "Calibrated (<preregistration>)", "Uncalibrated: operating point thresholds", "Uncalibrated: global thresholds", or "Not used for routing". The head badge of the card and the engine card's router row read the same gate, so the calibration is shown from one source.

The page reads the engine view, the `judgment` and `model-router` settings sections, and the Laya view when it mounts, and re-reads them — with the router's gate, its pool status, and the model catalog — on `judgment/engines-updated`, on `settings/document-updated` for either namespace, on `llm/adapters-updated`, and on `connection/reset`. Before it first mounts, those invalidations only re-probe the engine view, which decides whether the entry is registered. Every write re-reads the page afterwards. The page model lives in the plugin's `apply` and reaches the component through the inject `hooks` compartment; the component holds no subscription of its own.

## Model Experience

None, as the page renders a browser configuration UI; nothing here reaches a model request.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

## Known Limitations and Deferred Work

- **No workspace overview** — the cross-session card arrives with its own Host read (`modelRouting.stats`) in a later change.
- **Overrides are read-only** — the Consumers list shows `judgment.overrides` but offers no editor; they are edited in `settings.yaml`.
- **Laya install progress is a state line** — the `laya` Remote reports whether an install is running, not how far it got; the row shows "Installing…" until the gateway state changes.
- **The Shadow mode is not offered** — the default-mode control shows only the modes that exist, Off and On.
- **The judge hint states the checkpoint context, not a measured head** — the load-time head check that would report the head-token figure of the last fitting limits has no Host surface yet; the hint names the Laya checkpoint context until one exists.
